# JTML v0.3.0-rc.2 — experimental technical tester candidate

[v0.3.0-rc.2 is published](https://github.com/mrjohnnyrocha/jtml/releases/tag/v0.3.0-rc.2)
from `13c53ab475c9e82ac4be2b232f744d664e926dea`. New users should go directly to
[install and run the Counter](#install-and-five-minute-first-app-smoke). No GitHub
Actions access, source build or author assistance is needed to download a package.
The binaries are unsigned/unnotarized and this is an experimental preview.

**Release versus main:** RC.2 has a confirmed component-input defect: assigning
state (including clearing it) does not update the displayed `input into` value.
The [input synchronization fix](../architecture/input-state-sync/README.md) is on
current main, not in RC.2. The [first-app form walkthrough](../getting-started.md)
uses current main for that reason. RC.2's `new app` also needs
`make Card title` changed to `export make Card title` in `components/card.jtml`.
That resolves import checking only on RC.2: its clean-production build still
rejects the imported component. PR #53 fixes both the generated export and
production import planning on current main; neither fix is in RC.2. Use the
bundled Counter below with this release, or build main for the modular starter.
The single-file `new` command generates a Classic compatibility example.

The preparation/approval sections below are historical maintainer context for
this exact release. They do not mean the public downloads are still awaiting
publication. Published artifact and physical macOS acceptance records are attached
to the release; any future replacement requires its own review.

## macOS artifact compatibility contract

**Do not use the macOS RC artifact from [run 40150110121](https://github.com/mrjohnnyrocha/jtml/actions/runs/40150110121)
on macOS 14.** Its checksums are valid, but both the CLI and C API declare minimum
macOS 15.0 (SDK 15.5) and import libc++ symbols absent on macOS 14.4.1. The CLI
aborts in dyld even for `--version`; any subsequent HTTP 404 is not an application
or server diagnosis. This failure was reproduced on a physical macOS 14.4.1 arm64
host. That artifact is not macOS 14-compatible and must be replaced, not relabeled.

Regenerated macOS RC packages use explicit `CMAKE_OSX_DEPLOYMENT_TARGET=14.0`
through the existing packager. Their `MACOS_COMPATIBILITY.json` audits **both**
CLI and C API extracted from the bundle and CPack archive: arm64, actual Mach-O
minimum OS 14.0, SDK, system dylibs, complete undefined-symbol lists, binary hashes,
and rejection of the two known incompatible exception symbols. Checksums and
source metadata must be regenerated for the exact clean corrective commit.
A lower minimum-OS header or a successful macOS 15 CI run alone does **not** prove
macOS 14 compatibility. Before sharing each replacement macOS artifact, download
it onto macOS 14.4.1 arm64, verify SHA256SUMS, and pass `--version`, check, static
browser build, Counter Add one/Reset, Studio startup/resources and a compiled
caller of the shipped C API. Record the exact source SHA, run and archive hashes.
See the [compatibility investigation](macos14-compatibility.md) for reproduction.

## Release scope and blockers

as 0.3.0-rc.2; produce both Ubuntu Linux and macOS packages; pass the existing
relocated bundle/CMake/CPack, compiled C API, notices/checksum/manifest and Studio
checks; pass the production-reference browser checks with clean browser exit;
retain matching source/version metadata and download checksums. A failure in either
platform blocks promotion of that platform. A green development build is inherited
baseline evidence, not proof that the RC packages passed.

**Recorded owner authority:** the owner confirmed the necessary rights and
Apache-2.0 distribution authority on 2026-10-26, preserving third-party terms and
previous licenses. The exact statement and resolved JSON snapshot provenance are
in the [licensing/provenance record](licensing-provenance.md). This is not an
approval of artifacts that have not yet been produced.

**Owner decisions, still required:** review the exact clean source SHA, both RC.2
platform artifacts, checksums and physical macOS 14.4.1 acceptance; accept the
experimental support boundary and choose whether/when to distribute the reviewed
files. A tag or official release remains a separate explicit decision. The
workflow never manufactures approval or publishes a release.

**Disclosed limitations, not automatically blockers for this bounded prerelease:**
five native complete-attribute renderer differences; reference microfixture HTML
99939 / 70000 bytes (source baseline; RC.2 artifacts still require verification);
experimental tooling/type/source-span coverage; unsigned and
unnotarized binaries; no Windows, Linux arm64, Intel Mac, universal macOS, Python
binding or VSIX artifact. The owner must accept this scope explicitly; no budget,
oracle or known-discrepancy catalog is changed to obtain a release pass.

## What's in RC.2

Friendly JTML 2 is the canonical authoring language: observable state/actions,
HTML-shaped UI and static browser output for validated application shapes.
Classic remains compatibility/embedding infrastructure; JTL remains experimental.
This RC packages the reviewed main after PR #47, including strict script-CSP root
events and root-conditional component lifecycle/public introspection fixes. The
RC.2 preparation itself adds no compiler/runtime behavior or language semantics.
The inherited PR #47 evidence is 476/476 CTests, the complete local gate with nine
clean-exit benchmarks, and exact-head Ubuntu/macOS CI; it is source-baseline
evidence, not a successful RC.2 artifact run. The shared-runtime baseline remains
271961 / 272000 bytes; no threshold changes are part of RC.2 preparation.

The distribution reuses the existing versioned CLI/C API packaging, relocatable
Studio data, deterministic archive container, complete notices, source identity
and clean-room installation checks. The command below selects rc.2 explicitly;
default source builds remain 0.3.0-dev. The independently versioned 0.2.0 editor
source is included for reference, not a published extension or promised versioned
ABI. `jtml_abi_version()` identifies the same distribution as the CLI.

| Surface | RC.2 technical testing contract |
| --- | --- |
| Ubuntu Linux x86_64 | Native build/test on `ubuntu-22.04`; no claim for other distros or older glibc/libstdc++ |
| macOS Apple Silicon arm64 | Intended minimum macOS 14.0; hosted build/test on `macos-15` arm64 with explicit 14.0 deployment target. Intel and other versions are unverified |
| Browser-local output | Four generated assets, counter and production-reference interactions, CSP-safe JS; application support remains bounded by existing production fixtures |
| Studio/tutorial/examples | Bundled resources discovered after relocation; loopback trusted-code tools, not a public server or sandbox |
| C API | Matching shipped header/library and compiled caller smoke; no stable cross-version ABI guarantee |

## Prepare and review exact RC artifacts

After this PR is merged, choose its reviewed merge SHA (or a later reviewed commit
containing these scripts). Run the workflow from the default branch; pass the full
40-character **source commit**, not a moving branch name:

```sh
gh workflow run rc-distribution.yml --ref main \
  -f source_revision=<FULL_REVIEWED_40_CHARACTER_SHA>
```

Use Actions → **RC distribution review** to follow both jobs. No upload step runs
if packaging, installation or browser checks fail. The download groups are named
`jtml-0.3.0-rc.2-linux-x86_64-<SHA>` and
`jtml-0.3.0-rc.2-darwin-arm64-<SHA>` (14-day review retention). Within each group:

- `jtml-0.3.0-rc.2-<platform>-<arch>.tar.gz`: primary tester bundle, extracts to `release/`.
- `jtml-0.3.0-rc.2-<platform>-<arch>-install.tar.gz`: alternative CPack install layout.
- `ARTIFACT.json`, `RC_REVIEW.json`, `BUILD_ENVIRONMENT.txt`, `SHA256SUMS`, these release notes and a feedback form.

The two layouts are alternatives from the existing packagers, not separate
compiler builds. The checksums cover all review payload files, including both
archives; the bundle also contains its own per-file checksums and relative manifest.
They detect changed bytes, not authenticity against a compromised download source.

To reproduce locally from the selected **clean checkout**:

```sh
git checkout --detach <FULL_REVIEWED_40_CHARACTER_SHA>
python3 tests/test_prepare_rc.py
python3 tests/test_macos_distribution.py
# macOS: the wrapper requires MACOSX_DEPLOYMENT_TARGET=14.0 (default).
python3 scripts/prepare_rc.py --source-revision "$(git rev-parse HEAD)"
```

The existing packager configures Release, Python off and suffix rc.2, then builds
CLI/C API. CPack runs **before** the final explicit install, preserving its correct
install manifest. All existing distribution tests run unchanged. `dist/rc-review/`
is the review payload; source SHA, dirty state, host and SHA-256 are recorded.
The manual workflow additionally invokes the existing browser reference with the
actual packaged RC CLI. Neither command tags, publishes, enables auto-merge nor
records owner approval. No new competing packaging implementation is introduced.

## Install and five-minute first-app smoke

Download the primary bundle for your OS and `SHA256SUMS` from the
[public release assets](https://github.com/mrjohnnyrocha/jtml/releases/tag/v0.3.0-rc.2).
The `-install` archive is an alternative layout, not an additional dependency.
The following commands download and verify just the primary bundle in a fresh
directory. `curl`, `tar` and a checksum utility are required; Python 3 is needed
only for the static server below.

```sh
mkdir jtml-rc2
cd jtml-rc2
case "$(uname -s)-$(uname -m)" in
  Linux-x86_64) target=linux-x86_64 ;;
  Darwin-arm64) target=darwin-arm64 ;;
  *) echo 'No RC.2 binary for this target'; exit 1 ;;
esac
base=https://github.com/mrjohnnyrocha/jtml/releases/download/v0.3.0-rc.2
curl -fLO "$base/jtml-0.3.0-rc.2-${target}.tar.gz"
curl -fLO "$base/SHA256SUMS"
# SHA256SUMS lists all four archives; verify the one you downloaded.
grep "  jtml-0.3.0-rc.2-${target}.tar.gz$" SHA256SUMS > selected.sha256
if [ "$target" = darwin-arm64 ]; then
  shasum -a 256 -c selected.sha256
else
  sha256sum -c selected.sha256
fi
# Continue only if the selected archive reports OK.
tar -xzf "jtml-0.3.0-rc.2-${target}.tar.gz"
cd release
./bin/jtml --version
# Must print: jtml 0.3.0-rc.2
./bin/jtml check examples/friendly_counter.jtml
./bin/jtml build examples/friendly_counter.jtml --target browser --out counter-dist
python3 -m http.server 8000 --bind 127.0.0.1 --directory counter-dist
```

Python 3 is only needed here to serve files; the installed CLI does not require
Python, CMake, Node or a C++ compiler to check/build applications. Open
[localhost:8000](http://localhost:8000). Success means **Friendly JTML Counter**,
Count: 0 initially, Count: 1 after **Add one**, then Count: 0 after **Reset**.
The README screenshot is the one-click state of this exact bundled source.
`counter-dist` must contain `index.html`, `jtml-runtime.js`, `components/index.js`
and `app.js`, with no compatibility update-plan file. Stop the server with Ctrl+C.

Then run `./bin/jtml studio --port 8001`; open localhost:8001, select Counter,
format/run it and open a lesson/reference entry. Success means nonempty samples,
lessons and reference/docs; shutdown with Ctrl+C. HTTP/WS bind to loopback (WS
port 8081). Ports must be available. Resources also work when invoking the absolute
binary path from another directory; compiler input/output paths remain explicit.
On macOS 14, `--version` must work before starting any HTTP server. A dyld error
is a binary compatibility failure; stop and report the package hash and message.
Unsigned macOS downloads may be blocked by local policy; report the exact message.
`doctor` remains a source-tree audit, not the installed-package acceptance command.
