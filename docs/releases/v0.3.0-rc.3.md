production-readiness claim.** No public tag, GitHub release or website deployment

manual publication decision. Preserve its artifacts and historical evidence.

## Version and distribution contract

CMake retains project version `0.3.0` and the normal source-build default `dev`.
The existing RC wrapper/workflow explicitly select suffix `rc.3`, producing
`0.3.0-rc.3` consistently in CLI, C API, CPack and `ARTIFACT.json`. A compiled C
caller checks the shipped header/library's version and rendering behavior. The
source-only editor remains independently versioned `0.2.0`; no VSIX is published.

| Target | Acceptance scope |
| --- | --- |
| Ubuntu 22.04 x86_64 | Existing `ubuntu-22.04` pipeline, exact packaged CLI/C API, clean-home/cwd checks, relocation, resource loading and Chromium. Other Linux distributions/architectures are not inferred. |
| macOS arm64 | Existing `macos-15` pipeline, explicit macOS 14.0 deployment target, extracted CLI/C API Mach-O/dylib checks. The exact downloaded archives also require physical macOS 14.4.1 startup/C API/browser acceptance before a macOS 14 compatibility claim. Intel/universal Macs and other OS versions remain unverified. |
| Browser | Counter, generated modular starter, CoffeeOrder (including visible reset), production reference and existing regression fixtures under strict script CSP. Keep the four production assets together; serve over HTTP. |
| Studio/live tools | Bundled resources and loopback trusted-code development backends, not a sandbox or supported public service. |

The packages remain unsigned/unnotarized. Hosted execution does not reproduce
Finder quarantine or every end-user security policy. System C/C++ libraries remain
host dependencies. Windows, Linux arm64, Python wheels and VSIX are outside this
candidate. Python bindings are disabled; no new sanitizer run is claimed.

## Prepare exact review artifacts

Use the existing **RC distribution review** workflow. While this preparation PR
is unmerged, run its workflow revision from `codex/rc3-preparation`; after a manual
merge, use `main`. Pin the **full source commit**, not a moving ref:

```sh
gh workflow run rc-distribution.yml --ref codex/rc3-preparation \
  -f source_revision=<FULL_40_CHARACTER_SOURCE_SHA>
```

The workflow has read-only repository permissions and uploads review artifacts
only. Both established platform jobs run the complete existing verification gate
with clean browser exits required, then the existing RC wrapper/packagers and
clean installation/relocation/C API/resource tests. Extracted, relocated primary
and CPack binaries then run the Counter, modular starter and CoffeeOrder under
strict CSP, using their shipped guide/example files and an isolated home/cwd.
The actual primary archive CLI also reruns the production reference, imported
component suite and all six clean/compat/debug input synchronization cases.
Compatibility is tested explicitly; it is never used to satisfy clean output.

Review groups are named `jtml-0.3.0-rc.3-<platform>-<arch>-<SOURCE_SHA>`:

- Primary bundle: `jtml-0.3.0-rc.3-<platform>-<arch>.tar.gz`, root `release/`.
- Alternative CPack layout: the same stem plus `-install.tar.gz`.
- `ARTIFACT.json`, `RC_REVIEW.json`, `BUILD_ENVIRONMENT.txt`, `SHA256SUMS`,
  `RELEASE_NOTES.md`, `FEEDBACK.md`, and macOS compatibility reports where applicable.

Separate `jtml-0.3.0-rc.3-verification-<platform>-<arch>-<SOURCE_SHA>` groups retain
full-gate logs, packaged browser reports/screenshots/traces and their hashes;
failed verification evidence is uploaded too, while failed packages are not
advertised as verified. Review artifacts expire after 14 days: preserve the exact
payload before expiry if it is selected for manual publication. Source SHA,
workflow/job identity, actual binary hashes, browser reports and archive checksums
must agree. Hash consistency alone is not execution or source authentication.

## Install a review bundle and run the first applications

Download both platform review groups' metadata to inspect provenance; choose the
primary archive for your actual platform. `linux-x86_64` is Ubuntu 22.04 x86_64;
`darwin-arm64` is Apple Silicon macOS. Download its group's `SHA256SUMS` too.
Do not use a future public release URL before publication.

```sh
# Run in a new directory containing the downloaded primary archive and manifest.
# Set platform to linux-x86_64 or darwin-arm64 to match your machine.
platform=darwin-arm64
grep "  jtml-0.3.0-rc.3-${platform}.tar.gz$" SHA256SUMS > selected.sha256
# macOS (use sha256sum -c selected.sha256 on Ubuntu):
shasum -a 256 -c selected.sha256
# Continue only after the selected archive reports OK.
tar -xzf "jtml-0.3.0-rc.3-${platform}.tar.gz"
cd release
./bin/jtml --version
# Must print jtml 0.3.0-rc.3.
./bin/jtml examples
./bin/jtml check examples/friendly_counter.jtml
./bin/jtml build examples/friendly_counter.jtml --target browser --out counter-dist
python3 -m http.server 8000 --bind 127.0.0.1 --directory counter-dist
```

Open localhost:8000. Counter must show 0, increment to 1, reset to 0 and reload to
0. Stop the server with Ctrl+C. Version/startup failure is a release blocker;
report the exact package hash and OS message. `doctor` audits source trees and is
not an installed-package acceptance command. Python 3 is needed for this static
server, not to run the CLI; CMake/C++/Node are not application package prerequisites.

From the extracted `release/` directory:

```sh
./bin/jtml new app modular
./bin/jtml check modular/index.jtml
./bin/jtml lint modular/index.jtml
./bin/jtml build modular --target browser --out modular-dist
python3 -m http.server 8000 --bind 127.0.0.1 --directory modular-dist
```

Both Card headings must render; Add one changes Count: 0 to Count: 1. Stop the
server. Copy the complete CoffeeOrder source from bundled `docs/getting-started.md`
to `coffee.jtml`, then:

```sh
./bin/jtml check coffee.jtml
./bin/jtml lint coffee.jtml
./bin/jtml build coffee.jtml --target browser --out coffee-dist
python3 -m http.server 8000 --bind 127.0.0.1 --directory coffee-dist
```

Complete the guide's seven browser checks: validation, Enter submission without
navigation, cup/total changes, saved receipt, **visible textbox Clear**, and reload.
RC.3 must pass Clear; the historical RC.2 failure is not an accepted RC.3 result.
All three clean apps contain `index.html`, `jtml-runtime.js`, `components/index.js`
and `app.js`, with no `jtml-update-plans.js`, compatibility references or eval/new
Function. Their tested script policy is `script-src 'self'`; inline styles need a
separate style policy. New assets must not be mixed with an older compiler's output.

## Known limitations and manual publication decision

- General slots remain incomplete: conditional slots may lose content, slotted
  child components may remain uninitialized, and input setters generated only
  inside caller slots can be absent. Avoid these shapes; they do not universally
  fail closed. The tested starter's simple text/button slots and CoffeeOrder's
  component-local input do not establish universal slot support.
- Five native-renderer attribute differences remain genuine failures. Browser
  success does not prove native/live equivalence.
- The production reference HTML is 99952 bytes against its unchanged 70000-byte
  microfixture budget; the shared runtime is 271961/272000 bytes. Existing strict
  microbenchmark budgets and assertions are unchanged. A full-gate pass does not
  erase the separately reported reference overage.
- Direct root-loop components, explicit root ID/programmatic select boundaries,
  incomplete type/source spans and the experimental tooling remain documented
  constraints. The single-file `new` generator still emits Classic compatibility
  syntax; Friendly JTML 2 remains canonical.
- No real paid-agent trial/provider validation, broad application parity,
  three-independent-developer study or production/enterprise readiness is claimed.

Manual publication is **NO-GO** until the exact candidate has passing Ubuntu and
macOS RC workflow evidence, current PR CI, both archived layouts' checksums and
packaged application results, physical macOS 14.4.1 acceptance of those same
hosted archives, and a separate owner publication decision. The preparation PR's
final evidence/verdict identifies whether these technical conditions passed; it
does not grant permission to publish. Rebuild/review if the source or any selected
artifact changes; do not substitute a local development executable or relabel RC.2.

The existing [licensing authority/provenance record](licensing-provenance.md),
Apache-2.0 project license and third-party notices remain in force and are copied
unchanged into both layouts. No new dependency/license is introduced. Earlier
RC.2 binaries, checksums, macOS acceptance and input-reset failure evidence remain
historical evidence, not RC.3 validation. Use [the feedback template](rc-feedback.md)
with exact source SHA, package hash, platform and a minimal reproduction.
