# JTML Deployment Guide

Use clean browser production output for supported browser-local apps. Event
handlers and reactive state run locally in generated JavaScript; a live JTML
server is not required. The bounded [preview contract](https://github.com/mrjohnnyrocha/jtml/blob/main/docs/releases/v0.3-readiness.md)
records the accepted shapes and unresolved defects.

## Local development backend

`jtml serve <file> --port 8000 --watch` and Studio bind HTTP and WebSocket to
loopback (WS port = HTTP port + 80). Host/Origin and cross-site checks protect
mutations independently of CORS. HTTP event fallback remains supported. These
servers execute trusted local JTML; they are not sandboxes or authenticated remote
services. Missing Origin is not authentication. No supported remote-access mode
or public reverse-proxy deployment is claimed.

## Install locally from source

From the repository root:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DJTML_BUILD_PYTHON=OFF
cmake --build build --target jtml_cli jtml_c --parallel
cmake --install build --prefix "$HOME/.local"
"$HOME/.local/bin/jtml" --version
"$HOME/.local/bin/jtml" check "$HOME/.local/share/jtml/examples/friendly_counter.jtml"
# Optional, for `jtml` commands in this terminal:
export PATH="$HOME/.local/bin:$PATH"
```

Data are installed under `share/jtml`, documentation/notices under
`share/doc/jtml`, and the C API library/header under `lib`/`include`. On macOS and
Linux, the CLI discovers these paths relative to its executable, including after
moving the installation prefix or launching through a symlink. CLI archives also
find resources relative to `bin/jtml`. Packaged resources take precedence over the
working directory. A source build finds resources beside its `build/` directory;
a standalone development binary without bundled data retains cwd-based discovery.
No source checkout path is compiled into installed resource discovery. Compiler
inputs and outputs still use the paths supplied by the caller.

Studio includes samples, reference/sidebar catalogs, lessons and docs in both
layouts; no `cd` into the archive or installed data directory is required.
`doctor` remains a source-tree audit, not an installed-package health command.
See the bounded [release golden path](../releases/v0.3-golden-path.md) for platform,
version, installation and provenance limits.

## Local artifacts (not published releases)

```sh
scripts/package_cli.sh dist/release
(cd build && cpack)
scripts/build_site.sh dist/site
```

The archive script can be invoked from an unrelated working directory using its
absolute path and an absolute output directory. Relative output arguments are
relative to the caller; the build and archive locations remain repository-relative.

Build both CLI and C API targets before CPack. The archive script builds them
itself. Default CLI/C API, CPack and archive identities are `0.3.0-dev`.
`JTML_VERSION_SUFFIX=rc.2 scripts/package_cli.sh dist/release` creates a local
`0.3.0-rc.2` candidate; an explicitly empty suffix maps to `0.3.0`. These commands
perform no tag or upload and do not establish release approval.
The archive contains LICENSE, THIRD_PARTY_NOTICES.md, full dependency license
texts, CLI/C API, docs, examples, lessons, Studio samples/reference/sidebar catalogs,
editor source, site source, manifest
and SHA256SUMS. ARTIFACT.json records full version, OS/architecture, source
revision, dirty state and source-date epoch. MANIFEST.txt uses relative paths;
archive ownership, modes, ordering and timestamps are normalized. Repacking the
same prepared tree with the same epoch is byte-reproducible; cross-toolchain
binary reproducibility is not claimed. Downloaded editor node_modules are intentionally excluded; this
is not a VSIX. Use explicit input paths outside the archive root. `dist/doctor.json`
is generated by the full source gate, not promised inside every archive.

The Studio distribution regression can be run after packaging:

```sh
python3 scripts/test_studio_distribution.py --archive dist/jtml-0.3.0-dev-darwin-arm64.tar.gz
```

Use the archive filename for your version/OS/architecture. This extracts and
moves the artifact outside the repository, uses a clean HOME/working directory,
checks version/check/browser build, compiles a C consumer against the distributed
header/library, and compares live Studio APIs with independent source catalogs.
It loads/formats samples, executes Counter, checks notices/manifests/checksums,
and tests a relocated copy of a default-layout CMake install. `--cpack-archive`
adds the same relocated CPack smoke; `--install-prefix` supplies an existing install
without moving it. `--expect-missing` remains a historical missing-catalog control.

JTML-owned material is Apache-2.0; third-party terms remain unchanged. The
[owner confirmation](../releases/licensing-provenance.md) is recorded and the
[RC.2 prerelease](https://github.com/mrjohnnyrocha/jtml/releases/tag/v0.3.0-rc.2)
is public; future artifacts still require their own source/acceptance review.

The site build is local-only and requires a JTML compiler for its genuine Counter
demo. The unverified `site/CNAME` for jtml.org was removed. The default publication
URL is `https://mrjohnnyrocha.github.io/jtml/`; relative assets also work at a domain
root. The separate Pages workflow permits deployment only by explicit manual
dispatch after repository activation; see [website launch](website-launch.md).
No DNS/domain ownership, Pages setting or deployment is changed by a local build.

## Browser Production Builds

Use this for deployable browser apps:

```sh
jtml build app.jtml --target browser --out dist
```

This is a clean production build by default. It writes:

- `dist/index.html`
- `dist/jtml-runtime.js`
- `dist/components/index.js`
- `dist/app.js`

Clean production output does not emit `jtml-update-plans.js`, does not expose
`compatibilityUpdatePlans`, does not enable synthetic imported-component stubs,
and refuses component shapes that still need the legacy compatibility/update-plan
fallback. If a build fails for that reason, the error should name the component,
source location when known, unsupported shape, and the migration command:

```sh
jtml build app.jtml --target browser --compat --out dist
```

Use `--compat` only as a temporary migration bridge. It emits the legacy
`dist/jtml-update-plans.js` asset for older/debug tooling.

Use `--debug` when you need source-rich compatibility metadata and fallback
telemetry while investigating compiler/runtime behavior:

```sh
jtml build app.jtml --target browser --debug --out dist-debug
```

`dist/app.js` exposes the formal browser build contract at
`window.jtml.browserBuild`:

- `version`
- `mode`: `prod`, `compat`, or `debug`
- `cleanProduction`
- `compatibility`
- `debug`
- `assets`
- `diagnostics.sourceSpans`
- `diagnostics.fallbackTelemetry`

`window.jtml.productionMode` remains as a compatibility alias for older local
tools; new integrations should read `window.jtml.browserBuild.mode`.

Every browser build validates its emitted asset schema before returning
success. Production validates the absence of legacy update-plan references and
source-rich component debug payloads, and the embedded client manifest is parsed
against a closed public runtime-plan/project schema. Compat/debug validate the
explicit legacy asset and mode flags. All modes reject shipped browser assets
containing runtime dynamic compilation (`new Function` / direct `eval`).

## Browser Assets

Directory builds copy a conservative public asset allowlist:

- files under `public/`
- files under `assets/`
- root web metadata files such as `favicon.ico`, `robots.txt`, `sitemap.xml`,
  `manifest.json`, `site.webmanifest`, `browserconfig.xml`, and `humans.txt`

Project-private files are not copied by default. That includes hidden paths,
`.env*`, `.jtml` sources, `node_modules`, `dist`, `build`, `target`,
`jtml_modules`, lockfiles, nested README files, and arbitrary nested folders
outside `public/` or `assets/`.

Symlinks are skipped intentionally. Put deployable assets in `public/` or
`assets/` directly until configurable include/exclude rules ship.

`jtml transpile <file> -o <output.html>` remains useful for one-off inline
browser artifacts and previews, but production asset-mode flags are only
supported by `jtml build --target browser`.

## Browser Runtime Benchmarks

`scripts/benchmark_runtime.sh` always runs static asset and
compatibility-shape checks. It also calls
`scripts/benchmark_browser_runtime.sh` when a Chrome/Chromium-family browser is
discoverable. Headless browser runs can be blocked by local sandboxing, GUI
permissions, or missing browser dependencies; in that case the browser portion
may skip in local developer environments.

For release CI or any environment where Chrome/Chromium is expected to work,
make the browser benchmark mandatory:

```sh
JTML_REQUIRE_BROWSER_BENCH=1 scripts/benchmark_runtime.sh
```

Set `JTML_BENCH_BROWSER=/absolute/path/to/chrome` to choose a specific browser
binary. A v0.3 preview candidate must pass with
`JTML_REQUIRE_BROWSER_BENCH=1` in at least one clean CI/browser environment.
`scripts/verify_all.sh` sets that flag itself, so the full predeploy gate fails
instead of silently skipping browser behavior when Chrome/Chromium is missing or
blocked.
The browser benchmark reports `browserExit=clean` when Chrome exits normally
and `browserExit=terminated-after-result` when the result was written but the
harness had to terminate Chrome after timeout. The latter is not clean browser-shutdown proof and does not satisfy the
v0.3 release acceptance contract. Set `JTML_BROWSER_BENCH_REQUIRE_CLEAN_EXIT=1` in CI
environments that should support normal Chrome/Chromium `--dump-dom`
termination; with that flag, `terminated-after-result` is fatal.

## Preview security and evidence limits

Host generated assets using a static file server with a suitable CSP. Keep
serve/Studio on loopback for trusted development code. Run `doctor --json` only
as a source-layout audit; a successful result is not semantic or release evidence.
Require all nine benchmarks with `JTML_BROWSER_BENCH_REQUIRE_CLEAN_EXIT=1` in
addition to the full local gate. Hosted CI does not run that complete local gate.
